# UD01: Inferencia Local, Mensajes y Contratos de Software

## Introducción
Esta unidad aborda la comunicación con modelos de lenguaje locales y el establecimiento de fronteras deterministas de control sobre sus salidas.

Aprenderás:
* Cómo funciona la inferencia sin estado (*stateless*) y por qué la aplicación debe gestionar el contexto conversacional.
* A estructurar diálogos mediante mensajes con roles explícitos (`system`, `user`, `assistant`).
* Los riesgos de procesar texto libre no estructurado en entornos de producción.
* A orientar la generación del modelo con esquemas JSON y validar las respuestas con contratos de datos en Pydantic.
* A separar responsabilidades entre contrato sintáctico, reglas de negocio y autorización.
* A verificar validaciones mediante pruebas automáticas con `pytest` independientes del modelo.
* El funcionamiento del *streaming* de respuestas preservando la validación del contenido completo.

#### Parte 1: El Experimento «¿Tiene Memoria el Servidor de Inferencia?»

Al interactuar con aplicaciones conversacionales comerciales, es habitual asumir intuitivamente que el modelo "recuerda" la conversación. Sin embargo, en el desarrollo de software es imprescindible distinguir tres planos:
- **HTTP sin estado (*stateless*):** El protocolo HTTP no conserva automáticamente el historial conversacional entre peticiones. Cada petición contiene la información que el servidor necesita para procesarla, salvo que la aplicación implemente mecanismos adicionales para identificar y recuperar ese estado.
- **Contexto explícito de inferencia:** Una petición no incorpora automáticamente el contenido de las peticiones anteriores. Si la aplicación necesita mantener una conversación, debe proporcionar de nuevo el contexto relevante.
- **Aplicación con estado:** Si la aplicación quiere mantener una conversación, debe conservar y gestionar el contexto que quiera proporcionar al modelo en cada nueva inferencia.

Crea el archivo `experimento_memoria.py` y ejecútalo con `uv run python experimento_memoria.py` para observar qué ocurre cuando realizamos dos llamadas HTTP independientes:

```python
# experimento_memoria.py
import httpx

url = "http://localhost:11434/api/generate"

print("--- PETICIÓN 1: Presentación ---")
res1 = httpx.post(url, json={
    "model": "qwen2.5:0.5b",
    "prompt": "Hola, me llamo Laura García.",
    "stream": False
}, timeout=30.0)
print("Modelo:", res1.json()["response"].strip())

print("\n--- PETICIÓN 2: Pregunta sobre el pasado ---")
res2 = httpx.post(url, json={
    "model": "qwen2.5:0.5b",
    "prompt": "¿Cuál es mi nombre?",
    "stream": False
}, timeout=30.0)
print("Modelo:", res2.json()["response"].strip())
```

> [!NOTE]
> **Lo que debes observar:**  
> Lo importante no es qué respuesta textual concreta devuelva el modelo en la segunda petición, sino constatar que **la segunda petición no contiene ninguna información de la primera**. El servidor de inferencia no recibe la cadena `"Laura García"` en esa segunda inferencia.  
> 
> **Propiedad Arquitectónica:**  
> **Una petición de inferencia no incorpora automáticamente el historial de peticiones anteriores. Si una aplicación quiere mantener una conversación, debe conservar el contexto necesario y proporcionarlo en las siguientes inferencias.**

#### Parte 2: El «Chat Ingenuo» (Texto Concatenado en un Bucle)

Para que el modelo pueda responder con conocimiento del diálogo previo, la aplicación debe encargarse de conservar el contexto y enviarlo acumulado en cada turno:

```python
# chat_ingenuo.py
import httpx

url = "http://localhost:11434/api/generate"
contexto_texto = ""

print("Iniciando Chat Ingenuo (Escribe 'salir' para terminar)\n")

while True:
    mensaje = input("Usuario: ")
    if mensaje.lower() in ("salir", "exit"):
        break

    # Concatenamos la nueva pregunta al texto acumulado
    contexto_texto += f"\nUsuario: {mensaje}\nAsistente:"

    response = httpx.post(url, json={
        "model": "qwen2.5:0.5b",
        "prompt": contexto_texto,
        "stream": False
    }, timeout=30.0)

    respuesta = response.json()["response"].strip()
    contexto_texto += f" {respuesta}"

    print(f"Asistente: {respuesta}\n")
```

Si te presentas primero (*"Me llamo Laura"*) y después preguntas (*"¿Cuál es mi nombre?"*), observarás que ahora el modelo sí utiliza ese dato en su respuesta.

> [!IMPORTANT]
> **Pregunta de Ingeniería:** *¿Qué ha cambiado: el modelo o la información que la aplicación le proporciona?*  
> **Respuesta:** En esta arquitectura, la memoria conversacional no forma parte de los parámetros del modelo: la aplicación conserva el historial relevante y lo incorpora al contexto de las siguientes inferencias.

#### Parte 3: Del Texto Concatenado a los Mensajes Estructurados con Roles

El método ingenuo de concatenar texto plano (`Usuario: ... / Asistente: ...`) mezcla contenido y estructura en un mismo `string`. Las etiquetas son únicamente texto dentro del prompt, por lo que la aplicación está representando la estructura del mensaje y su contenido mediante la misma cadena de texto. Esto dificulta distinguir de forma explícita qué parte de la entrada corresponde a la estructura de la conversación y qué parte corresponde a los datos aportados por el usuario.

Para separar limpiamente la estructura de los datos del contenido, la API formal de chat (`POST /api/chat`) representa la conversación mediante una **lista de mensajes donde el rol y el contenido están representados como campos separados**:

```python
# chat_estructurado.py
import httpx

url = "http://localhost:11434/api/chat"

messages = [
    {
        "role": "system",
        "content": "Eres un asistente de atención técnica de una empresa. Responde de forma concisa y profesional."
    }
]

print("Iniciando Chat Estructurado con Roles (Escribe 'salir' para terminar)\n")

while True:
    prompt = input("Usuario: ")
    if prompt.lower() in ("salir", "exit"):
        break

    messages.append({"role": "user", "content": prompt})

    response = httpx.post(url, json={
        "model": "qwen2.5:0.5b",
        "messages": messages,
        "stream": False
    }, timeout=30.0)

    respuesta = response.json()["message"]["content"].strip()
    messages.append({"role": "assistant", "content": respuesta})

    print(f"Asistente: {respuesta}\n")
```

> [!TIP]
> ### 🧠 ¿Dónde está la memoria y qué consecuencias tiene?
>
> En una aplicación conversacional, la arquitectura básica es:
>
> ```text
> Usuario
>    │
>    ▼
> Aplicación
>    │
>    ▼ (historial de mensajes + nuevo mensaje)
> LLM
>    │
>    ▼ (genera respuesta)
> Aplicación actualiza historial
> ```
>
> **Consecuencia física fundamental:**  
> El historial consume parte de la **ventana de contexto (*Context Window*)**. Cada mensaje acumulado aporta tokens que forman parte del contexto utilizado en las siguientes inferencias.  
> 
> Esta limitación ayuda a entender por qué una aplicación no puede enviar indefinidamente todo el contenido disponible al modelo. En **UD02** veremos cómo **RAG** permite seleccionar dinámicamente la información relevante que se incorpora al contexto de una inferencia, en lugar de intentar saturar la ventana con todo el corpus de la empresa.

#### Parte 4: De la Conversación al Intento de Extraer Datos (*Crash & Learn*)

Cuando una aplicación necesita extraer datos de una conversación (por ejemplo, el nombre y correo de un cliente) para guardarlos en base de datos, la tentación habitual es pedirle al modelo que devuelva texto con instrucciones como: *"Devuélveme un JSON"*:

```python
# crash_script.py
import json
import httpx

prompt = "Extrae los datos del cliente: Me llamo Laura García y mi correo es laura@empresa.com. Devuélveme exclusivamente un JSON."

response = httpx.post(
    "http://localhost:11434/api/generate",
    json={"model": "qwen2.5:0.5b", "prompt": prompt, "stream": False},
    timeout=30.0
)

raw_text = response.json()["response"]
print("--- RESPUESTA BRUTA DEL MODELO ---")
print(raw_text)

print("\n--- INTENTO DE PARSEO DIRECTO ---")
try:
    data = json.loads(raw_text)
    print("Datos procesados con éxito:", data)
except json.JSONDecodeError as e:
    print(f"FALLO DE PARSEO: {e}")
```

#### Lo que debes observar
Ejecuta varias veces el experimento. Es posible que algunas respuestas puedan analizarse directamente con `json.loads()` y otras no (por ejemplo, si el modelo añade preámbulos conversacionales como *"¡Claro! Aquí tienes tu JSON:"* o marcas de markdown ````json```).

Si en tus ejecuciones el modelo devuelve JSON válido de forma consistente, no significa que `json.loads()` haya establecido un contrato; significa únicamente que esas respuestas concretas han cumplido el formato esperado.

Observa que el programa no dispone de ninguna garantía que permita asumir que la salida siempre cumplirá el formato esperado:
> **El problema no es que un LLM sea incapaz de generar JSON. El problema es que `json.loads()` no establece ningún contrato entre el modelo y nuestra aplicación. Simplemente intenta interpretar como JSON aquello que recibe.**

> [!IMPORTANT]
> **Tesis Central de la Frontera:**  
> **La salida de un LLM es una propuesta de datos, no un dato confiable por defecto. El contrato lo establece la aplicación: define la estructura esperada, valida la respuesta recibida y rechaza cualquier resultado que no cumpla las condiciones establecidas.**  
> 
> $$\text{LLM propone} \longrightarrow \text{Aplicación valida} \longrightarrow \text{Aplicación decide}$$
> 
> **Principio de No Confianza Ciega:**  
> **Cumplir el contrato no garantiza que la propuesta sea correcta, autorizada ni ejecutable.** Un esquema Pydantic valida que la forma y los tipos encajan; las capas posteriores de la aplicación deben comprobar las reglas de negocio, la autorización del usuario y la gobernanza antes de cualquier decisión o persistencia con consecuencias.

## 1.3 Etapa 3: Práctica Guiada — De los Mensajes al Contrato Estructurado con Pydantic

Aprenderás a construir una frontera de software donde la aplicación orienta la generación mediante esquemas estructurados y valida formalmente el resultado con Pydantic.

```text
                    LLM
                     │
              genera propuesta
                     ↓
        ┌─────────────────────────┐
        │       APLICACIÓN        │
        │                         │
        │ JSON Schema (guía)      │
        │        ↓                │
        │ Pydantic (contrato)     │
        │        ↓                │
        │ reglas de dominio       │
        │        ↓                │
        │ decisión / persistencia │
        └─────────────────────────┘
```

| Capa | Responsabilidad |
|---|---|
| **LLM** | Interpretar lenguaje natural / generar propuesta |
| **JSON Schema** | Orientar la forma de salida esperada en la inferencia |
| **Pydantic** | Verificar estructura, tipos y restricciones implementadas en el modelo |
| **Reglas de Dominio** | Determinar la admisibilidad de los valores según las reglas del negocio |
| **Aplicación** | Decidir y autorizar la operación |
| **Infraestructura** | Ejecutar bajo controles deterministas |

> [!NOTE]
> En esta práctica, algunas reglas de dominio se expresan mediante validadores Pydantic por simplicidad. Una misma implementación puede agrupar controles de distintas responsabilidades; para este módulo importa identificar **qué decisión protege cada control**, no únicamente en qué clase o archivo está implementado.

#### Paso 1: Añadir Pydantic al Entorno de Trabajo
Añade `pydantic` al entorno virtual de `ud01-contratos` que creaste en la Etapa 1:
```bash
uv add pydantic
```

#### Paso 2: Definir el Contrato de Datos con Pydantic
Crea el archivo `src/contratos.py`. Observa que en este primer paso definimos `email` como cadena de texto simple (`str`); la validación de formato la añadiremos después en la práctica autónoma:

```python
from pydantic import BaseModel, Field

class ContactoCliente(BaseModel):
    nombre: str = Field(description="Nombre completo del cliente", min_length=2)
    email: str = Field(description="Dirección de correo electrónico del cliente")
    intencion: str = Field(description="Intención principal declarada por el cliente")
```

#### Paso 3: Implementar el Cliente con Salida Estructurada y Validación en el Harness
Crea el archivo `src/cliente_ollama.py`:

```python
import httpx
from src.contratos import ContactoCliente

def extraer_contacto(texto_usuario: str) -> ContactoCliente:
    url = "http://localhost:11434/api/chat"
    
    messages = [
        {
            "role": "system",
            "content": (
                "Eres un extractor de datos de clientes. Analiza el mensaje del usuario y extrae "
                "los datos solicitados cumpliendo estrictamente con el esquema esperado."
            )
        },
        {
            "role": "user",
            "content": texto_usuario
        }
    ]
    
    # 1. Llamada HTTP: captura de errores de comunicación de infraestructura
    try:
        response = httpx.post(
            url,
            json={
                "model": "qwen2.5:0.5b",
                "messages": messages,
                "format": ContactoCliente.model_json_schema(), # Indicación de esquema para orientar la generación
                "stream": False
            },
            timeout=30.0
        )
        response.raise_for_status()
    except httpx.HTTPError as e:
        # Error de comunicación con la infraestructura
        raise ConnectionError(f"Error de comunicación con Ollama: {e}") from e

    raw_content = response.json()["message"]["content"]
    
    # 2. La Frontera de la Aplicación: Pydantic valida lo que el modelo propone.
    # Si la propuesta incumple el esquema o los tipos, model_validate_json eleva ValidationError directamente.
    return ContactoCliente.model_validate_json(raw_content)
```

> [!NOTE]
> **Esquema de Generación (`format`) vs Frontera de Confianza:**  
> Proporcionar un esquema al servidor de inferencia orienta la generación hacia la estructura esperada, pero no convierte la respuesta del modelo en una decisión de negocio ni elimina la necesidad de validarla en la frontera de la aplicación.

#### Paso 4: Ejecutar el script de prueba
Crea `main.py` y observa cómo la aplicación consumidora discrimina con precisión ambas categorías de error:

```python
from pydantic import ValidationError
from src.cliente_ollama import extraer_contacto

mensaje = "Hola, soy Laura García. Me interesa conocer precios de pavimentos para exterior. Mi correo es laura@empresa.com."

try:
    cliente = extraer_contacto(mensaje)
    print("--- CONTRATO VALIDADO CON ÉXITO ---")
    print(f"Tipo devuelto: {type(cliente)}")
    print(f"Nombre:        {cliente.nombre}")
    print(f"Email:         {cliente.email}")
    print(f"Intención:     {cliente.intencion}")
except ValidationError as e:
    # Error de contrato: el LLM produjo una propuesta no conforme al esquema o reglas
    print(f"Propuesta rechazada por el contrato de datos: {e}")
except ConnectionError as e:
    # Error de infraestructura: fallo de red o caída del servicio Ollama
    print(f"Error de infraestructura: {e}")
```

## 1.5 Etapa 5: Práctica Autónoma — Reglas de Dominio y Rechazo Controlado

La práctica autónoma se articula en tres partes consecutivas que consolidan el concepto de **frontera de control**:

#### Parte A: Restricciones de datos y reglas de dominio con `@field_validator`
Modifica `src/contratos.py` para añadir validaciones sobre el contenido (en esta actividad utiliza `@field_validator` para implementar explícitamente las reglas solicitadas, aunque existen otras formas de expresar restricciones cerradas en Pydantic):
1. **Validación didáctica mínima de email:** Para simplificar la actividad, se utilizará una validación didáctica mínima con `@field_validator("email")`: el valor debe contener exactamente un símbolo `@` y la parte posterior debe incluir al menos un punto (`.`). No se pretende implementar un validador completo de especificación RFC, sino demostrar la aplicación de una regla de formato.
2. **Lista cerrada de intenciones admitidas:** La intención debe pertenecer estrictamente a una lista de valores admitidos por el negocio: `{"consulta", "compra", "soporte"}`. Si el modelo propone cualquier otro texto (ej. `"reclamo"` o `"desconocido"`), el validador debe elevar un `ValueError` descriptivo (que Pydantic encapsulará automáticamente en un `ValidationError`).

> [!NOTE]
> **Distinción Conceptual Clave:**
> * **¿Cumple la estructura y las restricciones declaradas?** $\longrightarrow$ **Contrato de datos** (esquema Pydantic y tipos).
> * **¿Es admisible según las reglas del negocio?** $\longrightarrow$ **Regla de dominio** (valor admitido o no admitido).
> * **¿Tiene este usuario permiso para realizar la acción?** $\longrightarrow$ **Autorización** (control de acceso del sistema).

#### Parte B: Rechazo Controlado y Manejo de Errores
Modifica la función `extraer_contacto` en `src/cliente_ollama.py` para que ante una excepción `ValidationError`:
1. La aplicación **no se caiga** ni propague una excepción no controlada hacia las capas superiores.
2. Registre en consola o log el motivo exacto del rechazo.
3. Devuelva un resultado controlado que distinga entre una extracción conforme y una rechazada (por ejemplo, devolviendo una estructura que indique `valido=False` y el motivo del fallo).

> [!TIP]
> **Decisión de Ingeniería:**  
> La estructura concreta del resultado queda a criterio del alumno (por ejemplo, una tupla, un modelo Pydantic envoltorio de respuesta o un dataclass de resultado), pero la interfaz elegida debe ser **estable y explícita**, de manera que el código consumidor pueda distinguir ambos estados inequívocamente sin necesidad de inspeccionar cadenas de texto libres ni excepciones, e incluir el motivo del rechazo.

#### Parte C: Diagnóstico y Frontera de Control

> [!IMPORTANT]
> **El objetivo de esta parte no es conseguir que el LLM produzca una salida concreta, sino comprobar que, cuando la aplicación recibe una propuesta determinada, sus reglas de dominio la admiten o rechazan correctamente.**  
> Un modelo de lenguaje es un componente estocástico: genera propuestas y no tenemos garantía absoluta de su contenido lingüístico. Por tanto, no presupongas qué valor exacto generará.

Divide tu comprobación en dos dinámicas:

1. **Observación con el Modelo de Inferencia:**
   Envía mensajes variados a través de `extraer_contacto()` y observa el resultado de la aplicación, utilizando temporalmente trazas o depuración para inspeccionar la propuesta generada antes de su validación (`raw_content`):
   * **Caso 1 (prueba de la regla de email):** Proporciona un mensaje en el que la intención pueda identificarse claramente como una compra, pero utiliza un correo inválido (ej. `"Hola, quiero comprar pavimentos cerámicos. Mi correo es usuario@@correo."`). Observa la propuesta generada y comprueba que, si la intención es reconocida como `compra`, el fallo procede exclusivamente de la regla de email.
   * **Caso 2 (prueba de la regla de intención):** Proporciona un mensaje donde el cliente plantee una reclamación (ej. `"Hola, solo quiero presentar una reclamación por un pedido roto. Mi correo es laura@empresa.com."`). Verifica el resultado realmente generado por el modelo: si la intención propuesta no pertenece a `{"consulta", "compra", "soporte"}` (por ejemplo, propone `"queja"` o `"reclamacion"`), el contrato debe rechazarla. Si el modelo opta por clasificarla bajo un término admitido como `"soporte"`, la propuesta superará la frontera. **No presupongas qué valor concreto producirá el LLM**.

2. **Comprobación Determinista de la Frontera con Cargas JSON:**
   Para verificar las reglas de dominio de forma determinista y sin depender de la variabilidad estocástica del LLM, simula directamente las propuestas mediante `ContactoCliente.model_validate_json()`:
   * **Propuesta con email inválido:**  
     `'{"nombre": "Laura García", "email": "usuario@@correo", "intencion": "compra"}'`  
     $\rightarrow$ Se rechaza únicamente por el formato del email.
   * **Propuesta con intención no admitida:**  
     `'{"nombre": "Laura García", "email": "laura@empresa.com", "intencion": "reclamo"}'`  
     $\rightarrow$ Se rechaza por no formar parte del catálogo permitido por el negocio.
   * **Propuesta con múltiples defectos:**

## 1.6 Etapa 6: Prueba Automatizada con `pytest`

> [!IMPORTANT]
> **Observa que estos tests no llaman al LLM.**  
> La finalidad de esta suite es comprobar de forma determinista la frontera de validación de la aplicación, independientemente de qué modelo genere la propuesta:
> 
> ```text
>        LLM
>         │
>  propuesta variable
>         ↓
> ─── FRONTERA DE CONTROL ───
>         ↓
>   contrato Pydantic
>         ↓
>   reglas de dominio
>         ↓
>  tests deterministas
> ```
> 
> En ingeniería de software no testeamos el comportamiento probabilístico del modelo mediante pruebas unitarias; testeamos que **los controles de la aplicación rechazan los datos no conformes contemplados por el contrato y las reglas de dominio**.

Crea el archivo `tests/test_contratos.py` para verificar de forma determinista el comportamiento de tu contrato ante casos válidos, incumplimientos del contrato y rechazos de reglas de dominio:

```bash
uv add --dev pytest
```

```python
# tests/test_contratos.py
import pytest
from pydantic import ValidationError
from src.contratos import ContactoCliente

def test_contrato_valido_nominal():
    raw_json = '{"nombre": "Laura García", "email": "laura@empresa.com", "intencion": "compra"}'
    obj = ContactoCliente.model_validate_json(raw_json)
    assert obj.nombre == "Laura García"
    assert obj.email == "laura@empresa.com"
    assert obj.intencion == "compra"

def test_contrato_rechaza_campos_faltantes():
    # Falta email e intención
    raw_json = '{"nombre": "Laura García"}'
    with pytest.raises(ValidationError):
        ContactoCliente.model_validate_json(raw_json)

def test_contrato_rechaza_tipo_incompatible():
    # El nombre no puede ser una lista
    raw_json = '{"nombre": ["Laura", "García"], "email": "laura@empresa.com", "intencion": "compra"}'
    with pytest.raises(ValidationError):
        ContactoCliente.model_validate_json(raw_json)

def test_contrato_rechaza_nombre_demasiado_corto():
    # min_length=2
    raw_json = '{"nombre": "L", "email": "laura@empresa.com", "intencion": "compra"}'
    with pytest.raises(ValidationError):
        ContactoCliente.model_validate_json(raw_json)

def test_validador_rechaza_email_invalido():
    # Email con doble arroba y sin punto en dominio
    raw_json = '{"nombre": "Laura García", "email": "usuario@@correo", "intencion": "compra"}'
    with pytest.raises(ValidationError):
        ContactoCliente.model_validate_json(raw_json)

def test_validador_rechaza_intencion_no_admitida():
    # Intención no presente en la lista de valores admitidos por el dominio
    raw_json = '{"nombre": "Laura García", "email": "laura@empresa.com", "intencion": "reclamo"}'
    with pytest.raises(ValidationError):
        ContactoCliente.model_validate_json(raw_json)
```
