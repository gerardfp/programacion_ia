#### Parte 1: El Experimento «¿Tiene Memoria el Servidor de Inferencia?»

Al interactuar con aplicaciones conversacionales comerciales, es habitual asumir intuitivamente que el modelo "recuerda" la conversación. Sin embargo, en el desarrollo de software es imprescindible distinguir tres planos:
- **HTTP sin estado (*stateless*):** El protocolo HTTP no conserva automáticamente el historial conversacional entre peticiones. Cada petición contiene la información que el servidor necesita para procesarla, salvo que la aplicación implemente mecanismos adicionales para identificar y recuperar ese estado.
- **Contexto explícito de inferencia:** Una petición no incorpora automáticamente el contenido de las peticiones anteriores. Si la aplicación necesita mantener una conversación, debe proporcionar de nuevo el contexto relevante.
- **Aplicación con estado:** Si la aplicación quiere mantener una conversación, debe conservar y gestionar el contexto que quiera proporcionar al modelo en cada nueva inferencia.

Crea el archivo `experimento_memoria.py` y ejecútalo con `uv run python experimento_memoria.py` para observar qué ocurre cuando realizamos dos llamadas HTTP independientes:

```python
# experimento_memoria.py
import httpx

url = "http://localhost:11434/api/generate"

print("--- PETICIÓN 1: Presentación ---")
res1 = httpx.post(url, json={
    "model": "qwen2.5:0.5b",
    "prompt": "Hola, me llamo Laura García.",
    "stream": False
}, timeout=30.0)
print("Modelo:", res1.json()["response"].strip())

print("\n--- PETICIÓN 2: Pregunta sobre el pasado ---")
res2 = httpx.post(url, json={
    "model": "qwen2.5:0.5b",
    "prompt": "¿Cuál es mi nombre?",
    "stream": False
}, timeout=30.0)
print("Modelo:", res2.json()["response"].strip())
```

> [!NOTE]
> **Lo que debes observar:**  
> Lo importante no es qué respuesta textual concreta devuelva el modelo en la segunda petición, sino constatar que **la segunda petición no contiene ninguna información de la primera**. El servidor de inferencia no recibe la cadena `"Laura García"` en esa segunda inferencia.  
> 
> Una petición de inferencia no incorpora automáticamente el historial de peticiones anteriores. Si una aplicación quiere mantener una conversación, debe conservar el contexto necesario y proporcionarlo en las siguientes inferencias.

#### Parte 2: El «Chat Ingenuo» (Texto Concatenado en un Bucle)

Para que el modelo pueda responder con conocimiento del diálogo previo, la aplicación debe encargarse de conservar el contexto y enviarlo acumulado en cada turno:

```python
# chat_ingenuo.py
import httpx

url = "http://localhost:11434/api/generate"
contexto_texto = ""

print("Iniciando Chat Ingenuo (Escribe 'salir' para terminar)\n")

while True:
    mensaje = input("Usuario: ")
    if mensaje.lower() in ("salir", "exit"):
        break

    # Concatenamos la nueva pregunta al texto acumulado
    contexto_texto += f"\nUsuario: {mensaje}\nAsistente:"

    response = httpx.post(url, json={
        "model": "qwen2.5:0.5b",
        "prompt": contexto_texto,
        "stream": False
    }, timeout=30.0)

    respuesta = response.json()["response"].strip()
    contexto_texto += f" {respuesta}"

    print(f"Asistente: {respuesta}\n")
```

Si te presentas primero (*"Me llamo Laura"*) y después preguntas (*"¿Cuál es mi nombre?"*), observarás que ahora el modelo sí utiliza ese dato en su respuesta.

> [!NOTE]
> **¿Qué ha cambiado respecto a la Parte 1: el modelo o la información que la aplicación le proporciona?**  
>   En esta arquitectura, la memoria conversacional no forma parte de los parámetros del modelo: la aplicación conserva el historial relevante y lo incorpora al contexto de las siguientes inferencias.
>
> **¿Dónde está la memoria y qué consecuencias tiene?**
> En una aplicación conversacional, la arquitectura básica es:
>
> ```text
> Usuario
>  │
>  ▼
> Aplicación
>  │
>  ▼ (historial acumulado + nuevo mensaje)
> LLM
>  │
>  ▼ (genera respuesta)
> Aplicación actualiza historial
> ```
>
> **Consecuencia física fundamental:**  
> El historial consume parte de la **ventana de contexto (*Context Window*)**. Cada turno acumulado aporta tokens que forman parte del contexto utilizado en las siguientes inferencias.  
> 
> Esta limitación ayuda a entender por qué una aplicación no puede enviar indefinidamente todo el contenido disponible al modelo. En **UD02** veremos cómo **RAG** permite seleccionar dinámicamente la información relevante que se incorpora al contexto de una inferencia, en lugar de intentar saturar la ventana con todo el corpus de la empresa.

#### Parte 3: Del Texto Concatenado a los Mensajes Estructurados con Roles

El método ingenuo de concatenar texto plano (`Usuario: ... / Asistente: ...`) mezcla contenido y estructura en un mismo `string`. Las etiquetas son únicamente texto dentro del prompt, por lo que la aplicación está representando la estructura del mensaje y su contenido mediante la misma cadena de texto. Esto dificulta distinguir de forma explícita qué parte de la entrada corresponde a la estructura de la conversación y qué parte corresponde a los datos aportados por el usuario.

Para separar limpiamente la estructura de los datos del contenido, la API formal de chat (`POST /api/chat`) representa la conversación mediante una **lista de mensajes donde el rol y el contenido están representados como campos separados**:

```python
# chat_estructurado.py
import httpx

url = "http://localhost:11434/api/chat"

messages = [
    {
        "role": "system",
        "content": "Eres un asistente de atención técnica de una empresa. Responde de forma concisa y profesional."
    }
]

print("Iniciando Chat Estructurado con Roles (Escribe 'salir' para terminar)\n")

while True:
    prompt = input("Usuario: ")
    if prompt.lower() in ("salir", "exit"):
        break

    messages.append({"role": "user", "content": prompt})

    response = httpx.post(url, json={
        "model": "qwen2.5:0.5b",
        "messages": messages,
        "stream": False
    }, timeout=30.0)

    respuesta = response.json()["message"]["content"].strip()
    messages.append({"role": "assistant", "content": respuesta})

    print(f"Asistente: {respuesta}\n")
```

> [!NOTE]
> **Lo que debes observar:**  
>
> * **Separación entre estructura y contenido:** A diferencia de `chat_ingenuo.py`, la aplicación ya no manipula una única cadena de texto con etiquetas manuales (`"Usuario: ..."`), sino una colección de objetos (`dict`) donde los metadatos (`"role"`) están separados del texto (`"content"`). Si el usuario escribe dentro de su mensaje la palabra `"Asistente:"`, esta queda encapsulada dentro del campo `content` del rol `user`, sin confundirse con la estructura de la conversación.
> * **El papel del rol `system`:** El primer mensaje de la lista establece las pautas de comportamiento e instrucciones generales para el asistente antes de que comience el diálogo con el usuario.
> * **Límite importante (instrucción $\neq$ restricción de seguridad):** Aunque los roles organizan semánticamente el contexto, el contenido de `system` sigue siendo una **orientación probabilística** para la inferencia, no una barrera de seguridad determinista. Además, observarás que aunque la **entrada** (`messages`) ya está estructurada, la **salida** del modelo (`message.content`) sigue siendo **texto libre**.

#### Parte 4: De la Conversación al Intento de Extraer Datos (*Crash & Learn*)

Cuando una aplicación necesita extraer datos de una conversación (por ejemplo, el nombre y correo de un cliente) para guardarlos en base de datos, la tentación habitual es pedirle al modelo que devuelva texto con instrucciones como: *"Devuélveme un JSON"*:

```python
# crash_script.py
import json
import httpx

prompt = "Extrae los datos del cliente: Me llamo Laura García y mi correo es laura@empresa.com. Devuélveme exclusivamente un JSON."

response = httpx.post(
    "http://localhost:11434/api/generate",
    json={"model": "qwen2.5:0.5b", "prompt": prompt, "stream": False},
    timeout=30.0
)

raw_text = response.json()["response"]
print("--- RESPUESTA BRUTA DEL MODELO ---")
print(raw_text)

print("\n--- INTENTO DE PARSEO DIRECTO ---")
try:
    data = json.loads(raw_text)
    print("Datos procesados con éxito:", data)
except json.JSONDecodeError as e:
    print(f"FALLO DE PARSEO: {e}")
```

> [!NOTE]
> Ejecuta varias veces el experimento. Es posible que algunas respuestas puedan analizarse directamente con `json.loads()` y otras no (por ejemplo, si el modelo añade preámbulos conversacionales como *"¡Claro! Aquí tienes tu JSON:"* o marcas de markdown ```` ```json``` ````).
>
> Si en tus ejecuciones el modelo devuelve JSON válido de forma consistente, no significa que `json.loads()` haya establecido un contrato; significa únicamente que esas respuestas concretas han cumplido el formato esperado.
>
> Observa que el programa no dispone de ninguna garantía que permita asumir que la salida siempre cumplirá el formato esperado:
>
> El problema no es que un LLM sea incapaz de generar JSON. El problema es que `json.loads()` no establece ningún contrato entre el modelo y nuestra aplicación. Simplemente intenta interpretar como JSON aquello que recibe.

#### Parte 5: El Peligro de Ejecutar Texto Libre Directamente (💀💀💀💀💀)

En la Parte 4 comprobamos qué ocurre cuando intentamos parsear texto libre esperando que sea un JSON válido. El problema se vuelve crítico cuando alguien intenta construir un «agente autónomo» conectando directamente la salida textual del modelo con la ejecución de comandos del sistema operativo (`subprocess.run(comando, shell=True)`), confiando únicamente en que el prompt del sistema le pide: *"Devuelve únicamente el comando que deseas ejecutar, sin explicaciones ni Markdown"*.

> Ejecuta el agente con la tarea por defecto o proponle otras tareas y analiza qué sucede en cada iteración:
>
> * **El prompt no impide que el modelo devuelva formato o explicaciones:** A pesar de la instrucción *"Devuelve únicamente el comando que deseas ejecutar, sin explicaciones ni Markdown"*, el modelo incluye con frecuencia bloques ```` ```bash ... ``` ````, comentarios previos o varios pasos mezclados con texto natural.
> * **Ejecución literal y errática en la terminal:** Como la aplicación ejecuta directamente `subprocess.run(comando, shell=True)`, Bash intenta interpretar las comillas de Markdown o las explicaciones en español como si fueran comandos de Linux (`command not found`, errores de sintaxis o redirecciones involuntarias).
> * **Ausencia total de estructura y validación:** La aplicación no sabe si el texto recibido es realmente un comando, una explicación o el final de la tarea (que se comprueba de forma frágil buscando la subcadena `"TAREA_COMPLETADA" in comando`), ni valida qué acción ni con qué argumentos se pretende ejecutar antes de lanzarla como `root`.

> [!IMPORTANT]
> **Tesis Central de la Frontera:**  
> Nunca se debe ejecutar ni procesar directamente el texto libre que devuelve un modelo. La salida de un LLM es una propuesta no verificada: debe estar estructurada bajo un esquema explícito y ser validada formalmente en la aplicación (por ejemplo, mediante contratos en Pydantic) antes de tomar cualquier decisión o ejecutar cualquier acción.
> 
> $$\text{LLM propone} \longrightarrow \text{Aplicación valida (Pydantic)} \longrightarrow \text{Aplicación decide}$$
> 
> **Principio de No Confianza Ciega:**  
> Cumplir el contrato no garantiza que la propuesta sea correcta, autorizada ni ejecutable. Un esquema Pydantic valida que la estructura, los campos y los tipos encajan; las capas posteriores de la aplicación deben comprobar las reglas de negocio, la autorización del usuario y la gobernanza antes de cualquier ejecución o persistencia con consecuencias.

## 1.2 Etapa 2: Cuestionario Conceptual <br><br> Antes de Ver el Código

Responde a estas 9 cuestiones fundamentales en tu cuaderno de trabajo antes de continuar:

1. **Estado HTTP y Memoria:** ¿Por qué una petición HTTP aislada no mantiene automáticamente el contexto de una conversación con un LLM?
2. **Responsabilidad de la Memoria:** ¿Por qué en esta arquitectura la memoria conversacional no forma parte de los parámetros del modelo y qué papel cumple la aplicación al conservar e incorporar el contexto en cada inferencia?
3. **Semántica de Roles:** ¿Qué aporta separar la conversación en una lista de mensajes estructurados (`system`, `user`, `assistant`) frente a concatenar texto plano con etiquetas en un string único?
4. **Límites de la Ventana de Contexto:** ¿Qué ocurre a medida que el historial de mensajes crece indefinidamente en una conversación? ¿Por qué esta limitación física impide incluir "todo" el historial o todos los documentos de la empresa en el prompt?
5. **Frontera de Seguridad y Autorización:** ¿Por qué redactar en el prompt o en el rol `system` instrucciones como *"No permitas el acceso a usuarios no administradores"* o *"No utilices los comandos: nano, vim..."* no constituye un mecanismo real de control ni de autorización?
6. **Decisión y Frontera de Control:** **¿Quién decide si una respuesta del modelo puede utilizarse en el sistema?** ¿Por qué la salida del LLM debe tratarse como una propuesta no verificada y no como un dato definitivo?
7. **Riesgos de Ejecutar Texto Libre (`dangerous_tool_calling.py`):** En la Parte 5 de la Etapa 1, el prompt del sistema indica explícitamente *"Devuelve únicamente el comando que deseas ejecutar, sin explicaciones ni Markdown"*. ¿Por qué esta instrucción no basta para pasar la respuesta directamente a `subprocess.run(comando, shell=True)` y qué fallos técnicos y de seguridad se producen al hacerlo?
8. **Fragilidad del Control de Flujo sobre Texto Libre:** En `dangerous_tool_calling.py`, la aplicación intenta detectar si el agente ha terminado comprobando `if "TAREA_COMPLETADA" in comando:`. ¿Qué problemas tiene controlar el flujo de un programa buscando palabras clave dentro de una cadena de texto libre generada por el modelo?
9. **Necesidad de Salida Estructurada y Validación con Pydantic:** ¿Por qué antes de procesar datos o ejecutar acciones propuestas por un LLM es imprescindible exigir que la respuesta esté estructurada y validarla mediante un esquema en **Pydantic**, en lugar de operar directamente sobre el texto bruto devuelto por el modelo?

## 1.3 Etapa 3: Práctica Guiada <br><br> De los Mensajes al Contrato Estructurado con Pydantic

Aprenderás a construir una frontera de software donde la aplicación orienta la generación mediante esquemas estructurados y valida formalmente el resultado con Pydantic.

```text
                    LLM
                     │
              genera propuesta
                     ↓
        ┌─────────────────────────┐
        │       APLICACIÓN        │
        │                         │
        │ JSON Schema (guía)      │
        │        ↓                │
        │ Pydantic (contrato)     │
        │        ↓                │
        │ reglas de dominio       │
        │        ↓                │
        │ decisión / persistencia │
        └─────────────────────────┘
```

| Capa | Responsabilidad |
|---|---|
| **LLM** | Interpretar lenguaje natural / generar propuesta |
| **JSON Schema** | Orientar la forma de salida esperada en la inferencia |
| **Pydantic** | Verificar estructura, tipos y restricciones implementadas en el modelo |
| **Reglas de Dominio** | Determinar la admisibilidad de los valores según las reglas del negocio |
| **Aplicación** | Decidir y autorizar la operación |
| **Infraestructura** | Ejecutar bajo controles deterministas |

> [!WARNING]
> En esta práctica, algunas reglas de dominio se expresan mediante validadores Pydantic por simplicidad. Una misma implementación puede agrupar controles de distintas responsabilidades; para este módulo importa identificar **qué decisión protege cada control**, no únicamente en qué clase o archivo está implementado.

#### Paso 1: Añadir Pydantic al Entorno de Trabajo
Añade `pydantic` al entorno virtual de `ud01-contratos` que creaste en la Etapa 1:
```bash
uv add pydantic
```

#### Paso 2: Definir el Contrato de Datos con Pydantic
Crea el archivo `src/contratos.py`. Observa que en este primer paso definimos `email` como cadena de texto simple (`str`); la validación de formato la añadiremos después en la práctica autónoma:

```python
from pydantic import BaseModel, Field

class ContactoCliente(BaseModel):
    nombre: str = Field(description="Nombre completo del cliente", min_length=2)
    email: str = Field(description="Dirección de correo electrónico del cliente")
    intencion: str = Field(description="Intención principal declarada por el cliente")
```

#### Paso 3: Implementar el Cliente con Salida Estructurada y Validación en el Harness

def extraer_contacto(texto_usuario: str) -> ContactoCliente:
    url = "http://localhost:11434/api/chat"
    
    messages = [
        {
            "role": "system",
            "content": (
                "Eres un extractor de datos de clientes. Analiza el mensaje del usuario y extrae "
                "los datos solicitados cumpliendo estrictamente con el esquema esperado."
            )
        },
        {
            "role": "user",
            "content": texto_usuario
        }
    ]

    try:
        response = httpx.post(
            url,
            json={
                "model": "qwen2.5:0.5b",
                "messages": messages,
                "format": ContactoCliente.model_json_schema(), # Indicación de esquema para orientar la generación
                "stream": False
            },

    except httpx.HTTPError as e:
        # Error de comunicación con la infraestructura
        raise ConnectionError(f"Error de comunicación con Ollama: {e}") from e

    raw_content = response.json()["message"]["content"]
    
    # 2. La Frontera de la Aplicación: Pydantic valida lo que el modelo propone.

    return ContactoCliente.model_validate_json(raw_content)

   *(No olvides restaurar el `system prompt` original y el parámetro `format` al terminar tus pruebas).*

> [!NOTE]
> **Reflexión sobre la Generación Restringida (*Constrained Decoding*):**  
> * **Instrucción semántica (`system prompt`) vs Restricción sintáctica (`format`):** El `system prompt` actúa sobre el contexto semántico y orienta probabilísticamente qué contenido generar, mientras que el parámetro `format` activa en el motor de inferencia un mecanismo de **decodificación restringida** (basado en gramáticas o máquinas de estados sobre el JSON Schema) que filtra y bloquea en cada paso de generación aquellos *tokens* que romperían la sintaxis del esquema.
> * **El peso de los nombres de los campos y el límite del tipo `str`:** El motor fuerza a escribir las claves del JSON (`"nombre": "..."`, `"email": "..."`). Al estar los nombres de las propiedades dentro del texto que el modelo va completando, una clave llamada `"email"` empuja fuertemente al modelo a completar un correo; pero si el campo se llama `"contacto"`, basta que el prompt pida un teléfono (`"+34 654654654"`) para que el modelo lo escriba y supere el filtro porque sintácticamente sigue siendo un `string`.
> * **Por qué necesitamos las cuatro capas:** Ni el prompt, ni los nombres de los campos, ni `format` por sí solos garantizan reglas de negocio. Necesitamos combinar la guía semántica del prompt, la restricción sintáctica (`format`), la validación estructural en la frontera (`Pydantic`) y las reglas de dominio explícitas (que implementaremos en la Etapa 5).

## 1.5 Etapa 5: Práctica Autónoma <br><br> Reglas de Dominio y Rechazo Controlado

La práctica autónoma se articula en tres partes consecutivas que consolidan el concepto de **frontera de control**:

#### Parte A: Restricciones de datos y reglas de dominio con `@field_validator`
Modifica `src/contratos.py` para añadir validaciones sobre el contenido (en esta actividad utiliza `@field_validator` para implementar explícitamente las reglas solicitadas, aunque existen otras formas de expresar restricciones cerradas en Pydantic):
1. **Validación didáctica mínima de email:** Para simplificar la actividad, se utilizará una validación didáctica mínima con `@field_validator("email")`: el valor debe contener exactamente un símbolo `@` y la parte posterior debe incluir al menos un punto (`.`). No se pretende implementar un validador completo de especificación RFC, sino demostrar la aplicación de una regla de formato.
2. **Lista cerrada de intenciones admitidas:** La intención debe pertenecer estrictamente a una lista de valores admitidos por el negocio: `{"consulta", "compra", "soporte"}`. Si el modelo propone cualquier otro texto (ej. `"reclamo"` o `"desconocido"`), el validador debe elevar un `ValueError` descriptivo (que Pydantic encapsulará automáticamente en un `ValidationError`).
3. **Inspección del esquema y orientación semántica del modelo:**  
   Comprueba qué devuelve ahora `ContactoCliente.model_json_schema()`. Observarás que, a diferencia de usar tipos declarativos como `Literal["consulta", "compra", "soporte"]` (que añaden un `"enum"` al JSON Schema y fuerzan la decodificación restringida en Ollama), **`@field_validator` ejecuta código Python a posteriori y no modifica el JSON Schema exportado**.  
   Como consecuencia, el motor de inferencia sigue viendo `intencion` como un `string` libre y no sabrá qué palabras exactas admite tu negocio a menos que se lo indiques semánticamente. Actualiza la `description` del campo `intencion` en `ContactoCliente` (por ejemplo: `"Intención del cliente. Valores habituales: consulta, compra, soporte"`) para orientar al modelo sin bloquear el esquema en `format`, de modo que podamos comprobar cómo actúa el validador de Pydantic cuando el modelo propone un valor fuera de dominio.

> [!NOTE]
> **Distinción Conceptual Clave:**
> * **¿Cumple la estructura y las restricciones de formato declaradas?** $\longrightarrow$ **Contrato de datos** (esquema Pydantic, tipos y formato como el `email`).
> * **¿Es admisible según el catálogo o las reglas del negocio?** $\longrightarrow$ **Regla de dominio** (valores permitidos por el negocio como `intencion`).
> * **¿Tiene este usuario permiso para realizar la acción?** $\longrightarrow$ **Autorización** (control de acceso del sistema).

#### Parte B: Rechazo Controlado en `extraer_contacto` y Adaptación de `main.py`
En la Etapa 3 diseñamos `extraer_contacto()` dejando que `ValidationError` se propagara como excepción hasta `main.py`. Sin embargo, al integrar un componente estocástico como un LLM, que una propuesta sea rechazada por una regla de dominio no es un fallo excepcional del programa, sino un **resultado operativo previsible** que conviene gestionar mediante un flujo de retorno explícito:

1. **Modifica `extraer_contacto` en `src/cliente_ollama.py`** para que envuelva `ContactoCliente.model_validate_json(raw_content)` en un bloque `try / except ValidationError`:
   * La aplicación **no se caiga** ni propague `ValidationError` hacia las capas superiores (mantén únicamente la propagación de `ConnectionError` ante fallos de red de `httpx.HTTPError`).
   * Registre en consola o log el motivo exacto del rechazo.
   * Devuelva un **resultado controlado** que distinga entre una extracción conforme (`valido=True` y el objeto `ContactoCliente`) y una rechazada (`valido=False` y el motivo del fallo).
2. **Adapta `main.py`:** Actualiza el script consumidor `main.py` para que utilice la nueva estructura de resultado devuelta por `extraer_contacto()` (comprobando explícitamente si el resultado fue válido o rechazado en lugar de capturar `ValidationError`), manteniendo el `except ConnectionError:` para los fallos de infraestructura.

> [!TIP]
> **Decisión de Ingeniería:**  
> La estructura concreta del resultado queda a criterio del alumno (por ejemplo, un modelo Pydantic envoltorio `ResultadoExtraccion`, un `dataclass` o una tupla), pero la interfaz elegida debe ser **estable y explícita**, de manera que `main.py` pueda distinguir ambos estados inequívocamente sin necesidad de inspeccionar cadenas de texto libres ni capturar `ValidationError`, e incluir el motivo del rechazo.

## 1.7 Etapa 7: Observación de Streaming, Evidencias y Defensa Técnica

#### Demostración Práctica: Streaming, Latencia (TTFT) y Validación Diferida
En las interfaces conversacionales para humanos es habitual activar el modo *streaming* (`"stream": True`) para mostrar las palabras a medida que se generan, reduciendo la latencia percibida por el usuario. Sin embargo, ¿qué ocurre cuando combinamos *streaming* con contratos de datos en Pydantic?

Crea el archivo `experimento_streaming.py` y ejecútalo con `uv run python experimento_streaming.py`:

```python
# experimento_streaming.py
import json
import time
import httpx
from pydantic import ValidationError
from src.contratos import ContactoCliente

url = "http://localhost:11434/api/chat"
payload = {
    "model": "qwen2.5:0.5b",
    "messages": [
        {
            "role": "system",
            "content": "Extrae los datos del cliente según el esquema solicitado."
        },
        {
            "role": "user",
            "content": "Hola, soy Laura García (laura@empresa.com) y mi intención es realizar una compra."
        }
    ],
    "format": ContactoCliente.model_json_schema(),
    "stream": True
}

print("Enviando petición en modo streaming...\n")
inicio = time.perf_counter()
ttft_ms = None
acumulado = ""

with httpx.stream("POST", url, json=payload, timeout=30.0) as response:
    response.raise_for_status()
    for linea in response.iter_lines():
        if not linea:
            continue
        chunk = json.loads(linea)
        fragmento = chunk.get("message", {}).get("content", "")
        
        if fragmento and ttft_ms is None:
            ttft_ms = (time.perf_counter() - inicio) * 1000
            print(f"[TTFT alcanzado en {ttft_ms:.1f} ms] Primer fragmento recibido: {fragmento!r}")
            try:
                ContactoCliente.model_validate_json(fragmento)
            except ValidationError:
                print(" -> Intento de validar en el primer token: FALLO (el JSON aún está incompleto)\n")
            print("Recibiendo stream en tiempo real: ", end="", flush=True)

        print(fragmento, end="", flush=True)
        acumulado += fragmento

latencia_total_ms = (time.perf_counter() - inicio) * 1000
print(f"\n\n[Stream finalizado en {latencia_total_ms:.1f} ms]")
print(f"Diferencia percibida (Latencia Total - TTFT): {latencia_total_ms - (ttft_ms or 0):.1f} ms\n")

print("--- VALIDACIÓN EN LA FRONTERA AL CIERRE DEL STREAM ---")
try:
    cliente = ContactoCliente.model_validate_json(acumulado)
    print("Contrato validado con éxito al completar el flujo:", cliente)
except ValidationError as e:
    print("Propuesta rechazada tras completar el flujo:", e)
```

> [!NOTE]
> **Lo que debes analizar tras ejecutar el experimento:**
> 1. **Time to First Token (TTFT) vs Latencia Total:** Compara los milisegundos que tarda en llegar el primer fragmento frente al tiempo total de generación. El *streaming* mejora drásticamente la respuesta visual percibida por una persona, pero no reduce el tiempo total que tarda en construirse el objeto completo.
> 2. **Disyuntiva de Arquitectura (UX vs Lógica de Negocio):** Mientras el flujo está abierto, la aplicación solo tiene fragmentos parciales de texto (`{"`, `"nombre"`, `": "Laura`...) que no son JSON válido ni han superado ninguna regla de dominio. Por tanto, en ingeniería de software hay que separar estrictamente **renderizar texto progresivo en pantalla** de **validar y ejecutar una operación de negocio**, la cual exige esperar al cierre del flujo y validar el mensaje íntegro en la frontera.

## 1.8 Go Beyond <br><br> De las Salidas Estructuradas a los Modelos de Decisión

> [!TIP]
> **Reto Opcional de Profundización Autónoma (*Go Beyond*):**  
> Esta sección es **opcional** y está pensada para que explores por tu cuenta una tendencia emergente en la ingeniería de software con IA: el paso de forzar a un LLM generativo a escribir JSON hacia el uso de **modelos de decisión (*decision models*)** especializados —como **Jev** (TypeSafe AI) y sus alternativas de pesos abiertos (`openJev`, `smalljev`)— diseñados para tomar decisiones tipadas en una sola pasada.

Hasta ahora hemos utilizado un **LLM generativo** (`qwen2.5:0.5b`) restringiendo su salida mediante un esquema JSON (`format`) y validándola en la frontera con **Pydantic**. Esta arquitectura es idónea cuando necesitamos extraer múltiples campos textuales (`nombre`, `email`, resúmenes o argumentos complejos). Sin embargo, en muchos puntos de una aplicación no queremos generar texto ni extraer entidades abiertas, sino **tomar una decisión discreta de control de flujo**: clasificar una consulta, decidir a qué departamento enrutar un ticket o evaluar el nivel de urgencia.

---

### 1. Diferencias entre un LLM Generativo y un *Decision Model*

Aunque ambos se apoyan en arquitecturas Transformer, resuelven problemas computacionales distintos:

```text
LLM GENERATIVO CON SALIDA ESTRUCTURADA (Autorregresivo — Token a Token)
───────────────────────────────────────────────────────────────────────
Entrada ──► [LLM] ──► "{" ──► "\"cat\":" ──► "\"TECNICA\"" ──► "}" ──► Pydantic ──► "TECNICA"
                       ▲
             Genera caracteres secuencialmente para construir un documento JSON

DECISION MODEL (~Jev — Evaluación Directa de Candidatos en Una Pasada)
───────────────────────────────────────────────────────────────────────
Entrada + Opciones ──► [Decision Model] ──► {TECNICA: 0.88, COMERCIAL: 0.09, SOPORTE: 0.03}
                                                       │
                                                       ▼
                                            Aplicación aplica umbral ──► "TECNICA"
```

* **LLM Generativo (*System 2 / Text Generator*):** Su objetivo nativo es predecir el siguiente *token* de texto de forma autorregresiva ($P(t_i \mid t_{<i})$). Incluso cuando aplicamos decodificación restringida (`format`), el modelo sigue invirtiendo ciclos de cómputo en redactar carácter a carácter la sintaxis del JSON (`{`, `"`, `:`, `}`) y oculta tras una cadena final la incertidumbre real que tuvo al elegir ese valor.
* **Modelo de Decisión (*System 1 / Decision Model*, p. ej. `~jev`):** No genera prosa conversacional ni serializa estructuras JSON. Recibe un estado o contexto junto con una pregunta acotada y evalúa directamente las opciones candidatas en una sola pasada (*forward pass*), devolviendo **distribuciones de probabilidad calibradas** listas para conectarse con la lógica condicional (`if` / `match`) de la aplicación.

---

### 2. Las Tres Primitivas de Decisión: Binaria, Selección y Puntuación Ordinal

En el paradigma popularizado por modelos de decisión como **Jev**, las decisiones de software se formalizan en tres primitivas tipadas:

1. **Decisión Binaria (*Binary* / `Noul`):**  
   Evalúa si una condición o proposición se cumple (`Sí/No`, `True/False`), devolviendo directamente una probabilidad calibrada $p \in [0.0, 1.0]$.  
   * *Ejemplo en la empresa cerámica:* `¿El cliente solicita cancelar un pedido ya facturado?` $\rightarrow$ `0.94`.
2. **Selección entre Opciones (*Categorical* / `Choice`):**  
   Selecciona una única categoría dentro de un conjunto cerrado y mutuamente excluyente de $K$ opciones (`["TECNICA", "COMERCIAL", "SOPORTE"]`), devolviendo tanto la opción ganadora como el reparto de probabilidades entre todas las candidatas ($\sum p_i = 1.0$).  
   * *Ejemplo:* Clasificar la intención de entrada para enrutar el mensaje al subsistema correspondiente.
3. **Puntuación Ordinal (*Ordinal* / `Score`):**  
   Sitúa la entrada dentro de una escala graduada con orden semántico estricto (por ejemplo, `["baja", "media", "alta", "critica"]`). A diferencia de `Choice`, en una escala ordinal **el orden importa**: confundir urgencia *alta* con *crítica* es un desvío menor que confundir *baja* con *crítica*. Devuelve una puntuación continua ponderada por la probabilidad de cada nivel.  
   * *Ejemplo:* Evaluar el nivel de frustración o urgencia de una reclamación por rotura de palés.

---

### 3. Comparación: Texto Libre vs. JSON Validado vs. Decisión Tipada

| Dimensión | Texto Libre (Etapa 1) | JSON Validado con Pydantic (Etapas 3–5) | Decisión Tipada (*Decision Model* `~jev`) |
|---|---|---|---|
| **Salida del modelo** | Prosa abierta sin garantías sintácticas | Cadena JSON generada *token* a *token* y validada en frontera | Primitiva tipada (`Choice`, `Noul`, `Score`) + vector de probabilidades |
| **Riesgo de fallo de parseo** | Alto (`JSONDecodeError`, bloques Markdown) | Muy bajo (controlado por `format` + `ValidationError`) | Nulo por diseño (no hay generación de texto ni serialización JSON) |
| **Visibilidad de la incertidumbre** | Nula (oculta en la redacción del texto) | Baja (devuelve la etiqueta elegida como si fuera absoluta) | **Alta y explícita** (expone la probabilidad asignada a cada opción) |
| **Latencia y coste por inferencia** | Variable según la verbosidad del modelo | Moderado (depende del número de *tokens* del esquema JSON) | **Mínimo** (una sola pasada sin generación autorregresiva de texto) |
| **Caso de uso óptimo** | Respuestas finales redactadas para lectura humana | Extracción de entidades y estructuras compuestas (`nombre`, `email`, listas) | Clasificación, enrutamiento (*routing*), *guardrails* y reglas de triaje |

---

### 4. Interpretación de Probabilidades, Incertidumbre y Umbrales

Cuando un LLM generativo devuelve `{"categoria": "COMERCIAL"}`, tu aplicación recibe exactamente el mismo objeto tanto si el modelo estaba seguro al $99\,\%$ como si dudaba casi a partes iguales entre dos opciones ($36\,\%$ `COMERCIAL`, $34\,\%$ `TECNICA`, $30\,\%$ `SOPORTE`).

Un modelo de decisión devuelve explícitamente esa distribución de probabilidades, lo que permite a la ingeniería de la aplicación gobernar la **incertidumbre** mediante **umbrales de confianza (*thresholds*)**:

* **Alta confianza ($p_{\max} \ge 0.75$):** La aplicación enruta automáticamente la consulta al flujo correspondiente.
* **Zona de incertidumbre ($p_{\max} < 0.75$ o margen estrecho entre las dos primeras opciones):** La aplicación **no ejecuta a ciegas** la categoría ganadora; en su lugar, puede activar un flujo de contingencia, pedir aclaración al usuario o derivar el caso a revisión humana (*Human-in-the-Loop*).

> [!NOTE]
> **Conexión con la Tríada de Responsabilidades:**  
> El modelo de decisión **estima probabilidades**; la aplicación **define el umbral de aceptación y gobierna la decisión operativa**. Cambiar el umbral de riesgo del negocio (por ejemplo, subir de `0.70` a `0.90` para autorizar devoluciones automáticas) es una decisión determinista en el código Python, no un ruego en un prompt.

---

### 5. Límites: Una Salida Tipada NO Garantiza que la Decisión sea Correcta

> [!WARNING]
> **El Principio de No Confianza Ciega sigue vigente:**  
> Eliminar los errores de sintaxis JSON y recibir un tipo limpio con dos decimales de probabilidad (`choice="COMERCIAL"`, `confidence=0.92`) **no garantiza que la decisión sea semánticamente correcta ni segura para el negocio**.

Un modelo de decisión puede equivocarse —incluso con alta confianza aparente— ante:
* **Consultas multi-intención:** Un cliente pregunta por la resistencia al deslizamiento de un pavimento exterior (`TECNICA`) y en la misma frase reclama que dos cajas de su pedido llegaron rotas (`SOPORTE`). Forzar una única etiqueta con `Choice` amputa parte del problema real.
* **Entradas fuera de distribución o sarcasmo:** Mensajes que no encajan en ninguna de las categorías previstas, pero donde las probabilidades siguen sumando $1.0$ entre las opciones cerradas si no se modela una condición previa de pertinencia (p. ej. combinando un `Noul` de filtro con un `Choice`).
* **Manipulación adversaria (*Prompt Injection*):** Un texto malicioso diseñado para sesgar la clasificación hacia una cola menos supervisada.

Por tanto, una decisión tipada reemplaza ventajosamente la generación de texto en tareas de clasificación, pero **nunca sustituye las reglas de dominio, los controles de autorización ni la evaluación empírica sobre un conjunto de casos de prueba**.
